01 · Problem

The problem, in one line

An airline runs on one shared fact — who is on which seat of which flight. Today it lives in four disconnected files, so nothing agrees with anything else.

P-01

Duplicate seat allocation

Two counters sell 14A. Discovered at the gate.

P-02

Manifests that disagree

Ticketed, boarded and bag lists never reconcile in time.

P-03

Orphaned baggage

A bag tag with no traceable passenger behind it.

P-04

Redundancy & anomalies

Aircraft model and city retyped onto every booking row.

Problem statement. Design a normalised relational database that holds airports, routes, aircraft, seats, flights, fares, passengers, bookings, tickets, check-ins, baggage, cancellations and payments as a single authoritative record; enforces the airline's rules inside the database; stays correct when two agents book the same seat at the same instant; and serves a role-based web application.
02 · Scope & objectives

What is in, what is out, and why

◤ In scope
  • Airports, routes, aircraft types and fleet
  • Seat maps, flights, gates, actual times
  • Fares per flight per cabin class
  • Passengers, bookings (PNR), tickets, seats
  • Check-in, boarding pass, baggage
  • Cancellation, refund, payment
  • RBAC: roles, permissions, role dashboards
  • Eight SQL reports as views
◤ Out of scope
  • GDS / IATA interlining and codeshare
  • Dynamic revenue management
  • Crew rostering and duty-time legality
  • Frequent-flyer accrual and redemption
  • Cargo, maintenance (MRO), load sheets
  • Live payment-gateway authorisation
  • Airport slots and ATC integration
◤ Objectives
  • Model all thirteen named entities in a crow's-foot ERD
  • Normalise to 3NF, showing the FD that forced each split
  • Push each rule to the lowest layer that can enforce it
  • Guarantee one seat, one passenger under concurrency
  • Enforce least privilege through RBAC, not hidden buttons
  • Answer the operational day in SQL, not a manual merge
  • Index what is actually searched, and justify it

Five associative entities. TICKET (ternary M:N plus the optional seat) · FARE (flight × class, carries the price) · CHECK_IN and CANCELLATION (1:1 events with attributes of their own) · ROLE_PERMISSION (role × permission). A junction becomes an entity the moment it has attributes.
06 · Relational schema

Nineteen relations, normalised to 3NF

1NF · atomic values
Repeating passenger / seat / bag groups on one booking row
✔ Split into TICKET and BAGGAGE rows
2NF · no partial dependency
(flight_no, dep_date) → flight details
passport_no → passenger details
✔ Extract FLIGHT, PASSENGER, SEAT
3NF · no transitive dependency
flight → aircraft → type → model, capacity
route → airport → city
✔ Extract AIRCRAFT_TYPE, AIRPORT, CABIN_CLASS, FARE

Every relation is in 3NF — and in BCNF: in each, every determinant is a candidate key. BOOKING.total_amount and CANCELLATION.refund_amount are derived values stored deliberately for auditability, reconciled inside the same transaction that changes their sources.

08 · Concurrency

Two agents, one seat 14A

The boundary case the whole design exists to survive. Two agents book the last seat on AI-2711 within the same few milliseconds.

Both transactions begin. Seat 14A is free; one seat remains.
T1 · Counter A
t
T2 · Counter B
Pessimistic

SELECT … FOR UPDATE takes the row lock; T2 blocks instead of reading stale data.

Declarative

UNIQUE(flight_id, seat_id) is the backstop — it holds even if the lock is forgotten.

Isolation

READ COMMITTED + FOR UPDATE; SERIALIZABLE only for the capacity phantom, with retry.

Scope

Seat holds are rows with an expiry — never an open transaction waiting on a human.

Boundary cases tested in Review 2. The last seat · capacity at exactly N vs N+1 · cancel and check-in at the same instant · retried payment callback (UNIQUE(txn_reference)) · double refund · midnight departure across time zones · refund after departure · abandoned seat hold · aircraft swap.

The target application

A Python (Flask) web app over the same schema. On login it reads ROLE_PERMISSION for the signed-in user and renders only the sections that role holds — booking desk, departure control, operations board, schedule builder, revenue, or user administration. Every route is guarded server-side; the database GRANTs are the second line, so a forged request still cannot read another passenger's PNR.
